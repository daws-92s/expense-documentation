# HTTP Status Codes

Every HTTP response carries a three-digit status code. The first digit tells you the class:

| Class | Meaning | Who is "at fault" |
|-------|---------|-------------------|
| **2XX** | Success | Nobody. It worked |
| **3XX** | Redirection | Nobody. Go look somewhere else |
| **4XX** | Client error | The request was wrong. Retrying the same request will fail again |
| **5XX** | Server error | The request was fine, but a server (or something behind it) failed |

This app can produce every code below. Each one is generated by a specific layer:

```
Browser ──► LB nginx ──► Frontend nginx ──► Backend (Node.js) ──► MySQL
            502/503/504   301/302/403/404    2XX/3XX/4XX/500/503
                          502/504
```

---

## Where to see the status code

| Where | How |
|-------|-----|
| The app itself | The **HTTP Activity Log** card lists every request with a coloured status pill |
| Browser | DevTools (F12) → **Network** tab → *Status* column. Click a row to see headers like `Location`, `Retry-After`, `Allow` |
| curl | `curl -i <url>` prints the status line and headers |
| Backend | `journalctl -u backend -f` shows lines like `PUT /transaction/3 200 12ms` |
| nginx (LB and frontend) | `tail -f /var/log/nginx/access.log` (status is the number after the request). Why a `5XX` happened is in `/var/log/nginx/error.log` |

For the curl examples, set this on any machine that can reach the LB:

```bash
LB=http://<LB-PUBLIC-IP>
```

## Using the playground

The **HTTP Status Code Playground** card in the UI has one button per code. Hover a button to see what it sends, click to send it. The result goes into the activity log. Most of the codes below can be triggered from there with one click. The ones that need you to stop a server are marked **(infra)**.

## 2XX: Success

| Code | Name | In the UI | curl |
|------|------|-----------|------|
| **200** | OK | Load the page, or click ✏️ on a row (fetches that expense) | `curl -i $LB/api/transaction` |
| **201** | Created | Add an expense | `curl -i -X POST $LB/api/transaction -H 'Content-Type: application/json' -d '{"amount":250,"category":"Food","description":"Lunch"}'` |
| **204** | No Content | Delete a single expense with 🗑 | `curl -i -X DELETE $LB/api/transaction/<id>` |

Things to point out:

- `201` includes a `Location: transaction/<id>` header telling you where the new resource lives.
- `204` has **no body at all**. Success is signalled by the code alone.
- Updating an expense (✏️ → change → **Update Expense**) is a `PUT` that returns `200` with the updated row.

## 3XX: Redirection

| Code | Name | Layer | In the UI | curl |
|------|------|-------|-----------|------|
| **301** | Moved Permanently | Frontend nginx | Open `http://<LB-PUBLIC-IP>/home`; the address bar changes to `/` | `curl -i $LB/home` |
| **301** | Moved Permanently | Backend | Playground → 301 | `curl -i $LB/api/transactions` |
| **302** | Found | Frontend nginx | Open `http://<LB-PUBLIC-IP>/docs`; you land on MDN | `curl -i $LB/docs` |
| **302** | Found | Backend | Playground → 302 | `curl -i $LB/api/latest` |
| **304** | Not Modified | Backend | Playground → 304 | see below |
| **304** | Not Modified | Frontend nginx | Reload the page and look at `style.css` / `app.js` in DevTools | see below |
| **308** | Permanent Redirect | Backend | Playground → 308 | `curl -i -L -X POST $LB/api/transactions -H 'Content-Type: application/json' -d '{"amount":10,"category":"Other","description":"via 308"}'` |

**301 vs 302.** `301` means "it moved for good, update your bookmarks", so browsers cache it. `302` means "go there for now". `/latest` is a `302` because the newest expense changes every time you add one.

**301 vs 308.** On a `301`, clients are allowed to turn a `POST` into a `GET`. `308` forbids that: the client must resend the same method and body. That is why `POST /transactions` uses `308`. With `-L`, curl follows it and you end with a `201`.

**304 step by step.** The server sends an `ETag` (a fingerprint of the response). The client sends it back in `If-None-Match`. If nothing changed, the server answers `304` with no body and the client reuses its copy:

```bash
# 1. get the ETag
curl -si $LB/api/transaction | grep -i etag
# ETag: W/"87-7W1JHFtg/3IKNdaGSNH/ZUpH0Lw"

# 2. send it back → 304
curl -i $LB/api/transaction -H 'If-None-Match: W/"87-7W1JHFtg/3IKNdaGSNH/ZUpH0Lw"'
```

Add an expense and repeat step 2 with the old ETag: now you get `200`, because the data changed.

nginx does the same for static files using `Last-Modified`:

```bash
curl -si $LB/static/css/style.css | grep -i last-modified
curl -i $LB/static/css/style.css -H 'If-Modified-Since: <paste the date>'
```

In the browser, 3XX codes are only visible in DevTools. JavaScript `fetch` follows redirects silently, so the activity log shows the final response and notes "browser followed redirect to …".

## 4XX: Client Error

| Code | Name | Layer | In the UI | curl |
|------|------|-------|-----------|------|
| **400** | Bad Request | Backend | Playground → 400 | `curl -i -X POST $LB/api/transaction -H 'Content-Type: application/json' -d '{"amount": 100,'` |
| **401** | Unauthorized | Backend | **Delete All** → leave token blank → OK | `curl -i -X DELETE $LB/api/transaction` |
| **403** | Forbidden | Backend | **Delete All** → type a wrong token | `curl -i -X DELETE $LB/api/transaction -H 'Authorization: Bearer wrong'` |
| **403** | Forbidden | Frontend nginx | Open `http://<LB-PUBLIC-IP>/admin` | `curl -i $LB/admin` |
| **404** | Not Found | Backend | Playground → 404 | `curl -i $LB/api/transaction/999999` |
| **404** | Not Found | Frontend nginx | Open `http://<LB-PUBLIC-IP>/no-such-page`; you see the custom 404 page | `curl -i $LB/no-such-page` |
| **405** | Method Not Allowed | Backend | Playground → 405 | `curl -i -X PATCH $LB/api/transaction` |
| **413** | Content Too Large | Backend | Playground → 413 | `curl -i -X POST $LB/api/transaction -H 'Content-Type: application/json' -d "{\"description\":\"$(head -c 20000 /dev/zero \| tr '\0' x)\"}"` |
| **415** | Unsupported Media Type | Backend | Playground → 415 | `curl -i -X POST $LB/api/transaction -H 'Content-Type: text/plain' -d 'amount=100'` |
| **422** | Unprocessable Content | Backend | Playground → 422 | `curl -i -X POST $LB/api/transaction -H 'Content-Type: application/json' -d '{"amount":-5,"category":"Crypto","description":""}'` |
| **429** | Too Many Requests | Backend | Playground → 429 | see below |

Things to point out:

- **400 vs 422.** `400`: the server can't even read the request (broken JSON). `422`: it can read it, but the values break the rules (negative amount, unknown category).
- **401 vs 403.** `401`: "who are you?" (no credentials, and the response has a `WWW-Authenticate` header). `403`: "I know who you are, and the answer is no" (wrong token, or `/admin`, which nginx denies to everybody).
- **405** comes with an `Allow` header listing what *is* allowed: `Allow: GET, POST, DELETE`.
- The UI's own form checks catch most mistakes before they're sent. The playground bypasses them on purpose to show what the server does.
- The real admin token is whatever `ADMIN_TOKEN` is set to in `backend.service` (default `admin123`).

**429 step by step.** Write requests (`POST`/`PUT`/`DELETE`) are limited to 10 per minute per client IP:

```bash
for i in $(seq 1 12); do
  curl -s -o /dev/null -w '%{http_code}\n' -X PUT $LB/api/transaction/1 -H 'Content-Type: application/json' -d '{}'
done
# 422 ... 422 429 429
curl -i -X PUT $LB/api/transaction/1 -H 'Content-Type: application/json' -d '{}' | grep -iE 'retry-after|ratelimit'
```

After this, adding or editing expenses from the same IP also returns `429` until the window resets (see `Retry-After`). Change the limit with `RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW_SEC` in `backend.service`.

## 5XX: Server Error

| Code | Name | Layer | How |
|------|------|-------|-----|
| **500** | Internal Server Error | Backend | Playground → 500, or `curl -i $LB/api/error` |
| **500** | Internal Server Error | Backend + MySQL | **(infra)** rename the table, see below |
| **502** | Bad Gateway | Frontend nginx | **(infra)** stop the backend |
| **502** | Bad Gateway | LB nginx | **(infra)** stop nginx on the frontend |
| **503** | Service Unavailable | Backend | Playground → 503, or `curl -i $LB/api/maintenance` |
| **503** | Service Unavailable | Backend | **(infra)** stop MySQL |
| **503** | Service Unavailable | LB nginx | **(infra)** `return 503` in `lb.conf` |
| **504** | Gateway Timeout | LB / frontend nginx | Playground → 504, or `curl -i $LB/api/slow` |

### 500: application bug

On the **MySQL** server, hide the table:

```sql
RENAME TABLE transactions.transactions TO transactions.transactions_bak;
```

Reload the UI. The list fails with `500`, and the backend log shows `ER_NO_SUCH_TABLE`. The database is up but the query is broken: a bug, not an outage. Restore:

```sql
RENAME TABLE transactions.transactions_bak TO transactions.transactions;
```

### 502: the upstream is down

On the **backend** server:

```bash
systemctl stop backend
```

Reload the UI → `502 Bad Gateway` on `/api/...`. Frontend nginx tried to connect to port 8080 and nobody answered. Its `error.log` shows `connect() failed (111: Connection refused) while connecting to upstream`. Opening `http://<LB-PUBLIC-IP>/api/transaction` directly shows the custom `50x.html` page. Restore with `systemctl start backend`.

Same idea one layer up: on the **frontend** server run `systemctl stop nginx`. Now the **LB** can't reach its upstream, and the whole page returns `502`. Restore with `systemctl start nginx`.

### 503: temporarily unavailable

**Database down.** On the **MySQL** server:

```bash
systemctl stop mysqld
```

The backend is still running but can't reach MySQL, so it answers `503` with `Retry-After: 30`. `curl $LB/api/health` shows `"db":"down"`. Compare this with the `500` above: `503` means "try again later", `500` means "something is broken". Restore with `systemctl start mysqld`.

**Maintenance at the LB.** On the **LB**, edit `/etc/nginx/nginx.conf` and uncomment:

```nginx
return 503 "Service temporarily unavailable";
```

Then run `systemctl reload nginx`. Every request now gets `503` from the LB without touching anything behind it. Comment it out and reload again to restore.

### 504: the upstream is too slow

`/api/slow` makes the backend wait 40 seconds before answering. nginx doesn't wait that long:

| Request | Who gives up | Result |
|---------|--------------|--------|
| `curl -i $LB/api/slow` | LB after 10s (`proxy_read_timeout 10s` in `lb.conf`) | `504` after ~10s |
| `curl -i http://localhost/api/slow` (run **on the frontend server**, skipping the LB) | Frontend after 30s (`proxy_read_timeout 30s` in `expense.conf`) | `504` after ~30s |
| `curl -i "$LB/api/slow?seconds=5"` | Nobody, 5s is under both limits | `200` after ~5s |

Try `?seconds=` values on either side of 10 to find the cut-off.

**502 vs 504.** `502`: the upstream is not answering at all (connection refused or a broken response). `504`: the upstream accepted the connection but took too long to reply.
